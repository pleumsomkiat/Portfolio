## เป้าหมายลำโพงในตัว G1 รุ่นปกติ และสถานะแอป

- ผู้ใช้ยืนยันว่าเป็น G1 รุ่นปกติ ใช้ Unitree Explore และต้องการเสริมภาษาไทย
  จากประสบการณ์เดิมจีน/อังกฤษ โดยเสียงต้องออกลำโพงในตัวหุ่น
- ผู้ใช้ยืนยันเว็บบนมือถือใช้งานได้ปกติแล้ว; ยังไม่ถือว่าระบบเสียงในหุ่นผ่าน
- Unitree Explore เปิดได้ แต่ผู้ใช้ล็อกอินไม่ได้ จึงยังไม่ทราบเฟิร์มแวร์หรือ IP ของหุ่น
- ขั้นถัดไป: แยกสาเหตุล็อกอินจากข้อความผิดพลาด แล้วตรวจการเชื่อมต่อแบบอ่านสถานะ
  ก่อนทดลองไฟล์เสียงไทยสั้น ๆ ผ่านช่องทางของหุ่น
- หลักฐานจากโค้ด unitree_ui มี G1-specific voice volume และ AudioHub API map;
  เป็นแนวทางที่ต้องพิสูจน์ ไม่ใช่ผลทดสอบบนหุ่นของผู้ใช้:
  https://github.com/legion1581/unitree_ui/blob/main/src/protocol/topics.ts
  https://github.com/legion1581/unitree_ui/blob/main/src/ui/components/audio-player.ts
- `ROBOT_AUDIO_ENABLED=false` ยังเป็นค่ารันจริง ไม่มีการเชื่อมต่อ ส่งเสียง หรือ
  เรียกคำสั่งการเคลื่อนไหวไปยังหุ่นระหว่างการตรวจเอกสารครั้งนี้

## ทดลอง Qwen3 และเคลียร์ไฟล์ชั่วคราว

- ผู้ใช้อนุญาตดาวน์โหลด Qwen3 4B เพื่อเปรียบเทียบ และให้กลับรุ่นเดิมหากไม่เหมาะ
- ดาวน์โหลด `qwen3:4b` ครบและตรวจ SHA-256; แท็กที่ได้ชี้ไปยัง
  Qwen3-4B-Thinking-2507 ซึ่งรองรับเฉพาะโหมดคิดละเอียด
- เทียบคำถามภาษาไทย 8 ข้อกับ `qwen2.5:3b` ด้วยคำสั่งและตัวเลือกชุดเดียวกัน
  โดยปล่อยระบบ STT ใช้ GPU ร่วมตามสภาพใช้งานจริง
- รุ่นใหม่ตอบวิทยาศาสตร์ตรงขึ้น แต่ค่ากลางเวลาตอบ 44.16 วินาที เทียบรุ่นเดิม
  1.83 วินาที และมี 2 คำถามหมดเวลาที่ 60 วินาที; ตัวเลขนี้เป็นชุดตัวอย่างเล็ก
  ไม่ใช่ผลรับรองความแม่นยำทุกคำถามหรือ benchmark มาตรฐาน
- `think:false` ไม่หยุดโหมดคิดของรุ่นที่โหลด และทำให้ข้อความคิดปนใน content;
  การลอง `/no_think` พร้อมตัวแยกข้อความคิดยังใช้ 18.98 วินาทีกับคำถามคณิตง่าย
- เลือกคง `qwen2.5:3b` สำหรับเว็บตามเงื่อนไขผู้ใช้ ไม่ได้นำผลคิดดิบไปให้เว็บอ่านเสียง
  และลบเฉพาะโมเดล Qwen3 ที่ดาวน์โหลดทดลองรอบนี้แล้ว; ไม่มีการดาวน์โหลดรุ่นอื่นเพิ่ม
- ค่ารันจริงยังเป็น `AI_PROVIDER=hybrid`, `HYBRID_AI_PROVIDER=ollama`,
  `OLLAMA_MODEL=qwen2.5:3b`; ข้อจำกัดความถูกต้องของโมเดลเดิมยังคงอยู่
- ล้างแคชและผลทดสอบเก่า 21 เป้าหมาย คืนพื้นที่ 1,973,132,364 bytes (ประมาณ 1.97 GB)
  ได้แก่ pip/npm cache, Next cache ที่เก็บเก่า, Chrome QA profiles และไฟล์ QA ที่สร้างได้ใหม่
- เก็บ `.venv`, `node_modules`, `.next` ที่ใช้อยู่, โมเดล STT, HTTPS/ใบรับรอง,
  ไฟล์ต้นฉบับ/อ้างอิง และรายงานเปรียบเทียบไว้; ตรวจขอบเขตพาธและ reparse points ก่อนลบ
- คืนการแก้ตัวเลือก context/temperature ที่ใช้เตรียมทดลองแล้ว ทดสอบ backend ทั้งชุด 169 รายการผ่าน
- ระหว่างตรวจท้าย คอมเปลี่ยนเครือข่ายจาก `10.19.171.153` เป็น `192.168.0.23`;
  ออกใบรับรองเซิร์ฟเวอร์ใหม่สำหรับ IP ปัจจุบันโดยใช้ CA เดิม และอัปเดต
  `DEV_ALLOWED_ORIGINS` พร้อมเปิด HTTPS proxy ใหม่ที่ `https://192.168.0.23:3443`
- ตรวจหลังจบการทดลองผ่าน HTTPS ใหม่: หน้าสนทนา/การตั้งค่า 200, คำตอบผู้บริหาร,
  คณิตศาสตร์ทั่วไปพร้อม MP3 ผ่าน (7.82 วินาทีรวมโหลดโมเดล/สร้างเสียง),
  ถอดคลิปสังเคราะห์หลังใช้งาน AI ตรง (1.60 วินาที) และตรวจเหลือโมเดลเดิมเพียงตัวเดียว
  ผลนี้เป็นการตรวจการทำงาน ไม่ใช่การรับรองความแม่นยำทั่วไปของรุ่นเดิม

- เปิด `AI_PROVIDER=hybrid` และ `HYBRID_AI_PROVIDER=ollama` ในเครื่องทดสอบ

  `keywords` เดิมยังเลือกใช้ได้
- เพิ่มฐานคำตอบจาก 19 เป็น 32 รายการ พร้อมแหล่งอ้างอิงและวันที่ตรวจสอบ
- เพิ่มผู้บริหารตามข่าวคณะวิศวกรรมศาสตร์ มช. เผยแพร่ 4 กันยายน 2569:
  คุณฉัตรชัย สมิตกาญจน์ กรรมการผู้จัดการ; คำตอบผูกกับวันที่ข่าว ไม่สรุปว่าเป็น
  เจ้าของ ผู้ถือหุ้น หรือทะเบียนรายชื่อผู้บริหารปัจจุบันทั้งหมด

## แก้พูดแล้วไม่มีข้อความ และนำส่วนเก็บเสียงคำถามออก

- ผู้ใช้แจ้งว่าพูดแล้วไม่มีข้อความขึ้น; ตรวจหน้าเว็บจริงพบ “ไม่พบคำพูดในไฟล์เสียง”
  และ API คืน 422 ซ้ำ 4 ครั้ง ทั้งเว็บและ API ยังทำงาน
- ตรวจไฟล์จากไมค์ที่เกิดปัญหา: ยาว 4.44 วินาที มีสัญญาณเสียง แต่ VAD .35/.2
  ไม่รับเป็นคำพูด; ลดเหลือ .1 พบสัญญาณ แต่ฝืนถอดโดยไม่ผ่าน gate แล้วข้อความไม่คงที่
  จึงคงตัวกรองและโมเดลเดิม แก้ทางรับเสียงแทน
- เครื่องมีไมค์ Microphone Array (Realtek). เปลี่ยนการขอเสียงจากเบราว์เซอร์เป็น
  `echoCancellation=false`, `noiseSuppression=false`, `autoGainControl=false`
  เพื่อส่งเสียงต้นฉบับเข้า STT; หน้าสนทนาหยุดเสียงตอบก่อนเริ่มรับคำถามตามเดิม
- หลังปรับ ผู้ใช้ยืนยันว่า “มีข้อความขึ้นแล้ว”; log รอบใช้งานจริงต่อมา 2 รอบผ่าน
  `/api/transcribe` 200 → `/api/chat` 200 → browser โหลดเสียงตอบได้ 206
- นำส่วนเล่นย้อนหลัง/ดาวน์โหลดและ Blob URL ของเสียงคำถามออกจากทั้งหน้าหลัก
  และหน้าทดสอบไมค์ตามคำขอ ใช้เสียงในหน่วยความจำระหว่างอัดและส่งเท่านั้น
- แสดงข้อผิดพลาดในบทสนทนาให้ชัดเจน เพิ่มชื่อไมค์และแถบระดับเสียงขณะรับคำถาม
- Frontend microphone tests 4 รายการและ TypeScript ผ่าน; เว็บและ health endpoint ตอบ 200
- ลบไฟล์ไมค์ชั่วคราวที่เก็บมาเพื่อตรวจอาการรอบนี้หลังวิเคราะห์ เก็บเฉพาะรายงาน
  `.runtime/microphone-failed-analysis.json`, `.runtime/failed-stt-diagnosis.json`
  และ `.runtime/failed-stt-standard-models.json` โดยไม่เก็บเสียงไว้ในรายงาน

ผลยืนยันว่าอาการไม่มีข้อความขึ้นกลับมาใช้งานได้ในรอบทดสอบของผู้ใช้ ยังไม่รับรอง
ความแม่นยำทุกประโยค; การเปลี่ยนรอบนี้ไม่เพิ่มการเดาคำถามหรือเดาคำตอบ.

- ในรอบนี้เคยเพิ่ม “ฟัง / ดาวน์โหลดเสียงคำถามล่าสุด” เพื่อใช้ตรวจ blob ที่ส่งเข้า Whisper;

  จากการเดา; ผลเทียบเสียงจริงจากคลิปโทรศัพท์ล่าสุดอยู่ในหัวข้อด้านบน
- ผลวิเคราะห์และภาพอยู่ใน `.runtime/user-clip-20261111/`; ไม่แก้หรือลบวิดีโอต้นฉบับ

## ชื่อ G1 และคำถามเรื่องความสามารถ

- ผู้ใช้พูด “G1 ทำอะไรได้บ้าง” แต่ภาพหน้าจอแสดงคำถามเป็น “กี่วันทำอะไรได้บ้าง”
  และได้คำตอบความสามารถของผู้ช่วยเว็บ จึงแยกแก้ทั้ง STT และการเลือกคำตอบ
- เปิดคำใบ้เฉพาะชื่อ `STT_HOTWORDS=G1, Unitree G1` และจัดรูปคำที่รู้จำชัดว่า
  จีวัน / จีหนึ่ง / G 1 ให้เป็น G1 โดยไม่มีกฎแทนคำระยะเวลา “กี่วัน”
- เทียบคลิปทดสอบชื่อสองรูปแบบ: เดิมได้ “ชีวัน...” / “ชี้หนึ่ง...” หลังปรับได้
  “G1 ทำอะไรได้บ้าง” ทั้งคู่; คลิป “กี่วันถึงจะส่งของ” และ “อีกกี่วันถึงวันศุกร์” ยังตรงเดิม
- เพิ่มคำตอบ `robot_capabilities` จากข้อมูล Unitree และจำกัดคำถามความสามารถ
  ของผู้ช่วยเว็บให้ชัดเจน ชื่อหรือหัวข้อที่ไม่เข้าใจจะไม่ตกไปตอบความสามารถเว็บ
- ทดสอบ backend 80 รายการผ่าน รวมรูปชื่อ G1 คำถามระยะเวลา และคำตอบแยกหุ่น/ผู้ช่วย
- ผ่านเว็บจริง: ถอดเป็น “G1 ทำอะไรได้บ้าง” → ตอบข้อมูลตัวหุ่น → โหลดเสียงตอบได้
- รายงาน: `.runtime/stt-g1-name/before.json`, `.runtime/stt-g1-name/hotwords.json`,
  `.runtime/g1-capabilities-smoke.json`

ผลข้างต้นยังใช้คลิปสังเคราะห์ในการทดสอบ ไม่ใช่คลิปจากไมค์ผู้ใช้ในภาพ.

## เร่งความเร็วการถอดเสียงล่าสุด

- เปลี่ยนบริการที่เปิดอยู่จาก CPU มาใช้ RTX 3050 ด้วย `STT_DEVICE=cuda`
  และ `STT_COMPUTE_TYPE=int8_float16`; ยังคงโมเดลไทยเดิมและ beam size 5
- ติดตั้ง NVIDIA cuBLAS 12.9.3.13, cuDNN 9.28.1.4 และ NVRTC 12.9.86
  ไว้ใน `.venv`; ตรึงเวอร์ชันที่ทดสอบใน `backend/requirements-gpu.txt`
- เพิ่ม `scripts/run_backend.sh` และ `scripts/run_python.sh` เพื่อเตรียมไลบรารี
  ก่อนเริ่ม Python และอุ่น CUDA/cuDNN ตอน startup
- Backend tests 64 รายการผ่าน; ข้อความจากสามคลิปเดิมตรงกันทั้ง CPU และ GPU
- เวลาทดสอบ CPU ค่ากลางสองรอบใน pipeline: 5.953 / 6.186 / 5.527 วินาที
- เวลาทดสอบ GPU ผ่านเว็บหลัง startup: 0.909 / 0.599 / 0.590 วินาที
  ตามลำดับ “ทำอะไรได้บ้าง”, “หนึ่งบวกหนึ่งได้เท่าไหร่”, “วันนี้อยากกินข้าวอะไรดี”
- ตัวเลขเป็นเวลาถอดเสียงคลิปสังเคราะห์สั้น ไม่รวมรอจบคำพูดหรือสร้างเสียงตอบ
- คงระยะรอเงียบ 1.6 วินาทีและเก็บท้ายเสียง 0.25 วินาที เพื่อไม่เพิ่มความเสี่ยงตัดคำ
- รายงาน: `.runtime/stt-speed-cpu-auto.json`, `.runtime/stt-speed-gpu.json`,
  `.runtime/stt-speed-web-gpu.json`

ใช้ `bash scripts/run_backend.sh` เมื่อเปิด backend ครั้งต่อไป เพื่อโหลดไลบรารี GPU.
เครื่องไม่มี GPU ใช้ `STT_DEVICE=cpu` และ `STT_COMPUTE_TYPE=int8` ได้ตามเดิม.

## พฤติกรรมปัจจุบันตามคำขอล่าสุด

- ส่วนถอดเสียงแสดงข้อความที่ถอดได้ตามเดิม ไม่มีการเอาคีย์เวิร์ดคำตอบไปแทนคำถาม
- เปลี่ยนโหมดตอบเป็น `AI_PROVIDER=keywords` ทั้งค่าเริ่มต้นและ `backend/.env`
- เลือกคำตอบตายตัวจาก `backend/knowledge/responses_th.json` จำนวน 19 รายการ
  ครอบคลุมความสามารถผู้ช่วย ข้อมูล G1 และข้อมูลบริษัทที่เตรียมไว้
- ไม่พบคีย์เวิร์ดที่รองรับหรือจับได้หลายเรื่องกำกวม: “ไม่เข้าใจคำถามครับ”
- รู้หัวข้อแต่ไม่มีข้อมูล เช่น อีเมล/ราคา หรือมีแค่ “บริษัท ออโต”: “ขออภัยครับ ผมยังไม่ทราบคำตอบสำหรับคำถามนี้ครับ”
- ไม่เรียก LLM หรือค้นเอกสารกว้าง ๆ เพื่อเดาคำตอบในโหมดนี้
- ไฟล์ JSON แก้คีย์เวิร์ด/คำถาม/คำตอบได้ โดยไม่ต้องรีสตาร์ต API
- ทดสอบ backend 80 รายการผ่าน รวมการไม่เรียก LLM การไม่ตอบข้อมูลผิดบริษัท/รุ่นหุ่นยนต์
  และการแยกข้อความถอดเสียงจากการเลือกคำตอบ
- ตรวจ `/health` ของบริการที่เปิดอยู่แล้ว: `ai_provider=keywords`
- ผ่านเว็บจริง 8 กรณี รวมคำถามที่รองรับ คำถามกำกวม บริษัทอื่น และ fallback
- เสียงตัวอย่าง “ทำอะไรได้บ้าง” → ถอดตรง → คำตอบตายตัว → โหลดเสียงตอบกลับได้:
  ถอดเสียง 6.28 วินาที เลือกคำตอบและสร้างเสียง 4.50 วินาที ไฟล์ MP3 76,176 bytes
- รายงาน: `.runtime/keyword-smoke.json` และ `.runtime/keyword-voice-smoke.json`

การเปลี่ยนส่วนตอบตามคีย์เวิร์ดไม่ได้ยืนยันว่าไมค์จริงถอดได้ตรงทุกคำ;
ปัญหาความแม่นยำของเสียงจริงยังต้องตรวจด้วยคลิปที่เกิดอาการตามบันทึกด้านล่าง.

## สถานะปัญหาไมค์จริง

ผู้ใช้ยังแจ้งว่าพูดแล้วถอดเป็นข้อความคนละอย่าง และระบุว่าใช้ไมค์คอม.
ตัวอย่างที่แจ้งล่าสุด: พูด “ทำอะไรได้บ้าง” แต่หน้าจอแสดง “บริษัท ออโต”.
ผลเสียงสังเคราะห์ก่อนหน้าไม่ยืนยันความแม่นยำกับไมค์จริง จึงยังไม่ถือว่า
ปัญหานี้หายแล้ว. ต้องเทียบเสียงต้นฉบับจากไมค์กับข้อความที่ถอดได้.

ตรวจประโยคตัวอย่างล่าสุดแยกตามชั้นแล้ว:

- กระบวนการ API/เว็บทำงานจากโฟลเดอร์นี้ ไม่พบตัวแปรแวดล้อมที่ทับคำใบ้ STT
  หรือเปลี่ยนปลายทาง API และไม่มีคำใบ้บริษัทในค่าปัจจุบัน
- เสียงสังเคราะห์ “ทำอะไรได้บ้าง” ใน WebM/Opus แบบปกติ เพิ่มช่วงเงียบ
  และลดระดับเสียง: API ถอดตรงทั้งสามแบบ ใช้เวลาประมาณ 4.5–4.7 วินาที
- ส่งข้อความ “ทำอะไรได้บ้าง” ไป `/api/chat` โดยตรง: ไม่ดึงฐานความรู้บริษัท
  และ AI ตอบเรื่องความสามารถสนทนา/ให้ข้อมูลตามปกติ
- ยังไม่มีคลิปจากไมค์ผู้ใช้ที่ถอดผิด จึงยังยืนยันสาเหตุของอาการจริงไม่ได้;
  ต้องขอคลิปจากปุ่มดาวน์โหลดในหน้า `/microphone` เพื่อทำซ้ำกับเสียงเดียวกัน
- รายงานเสียงตัวอย่าง: `.runtime/stt-capabilities/results.json`

- รีสตาร์ตทั้งเว็บและ API ให้โหลดการเปลี่ยนแปลงแล้ว

ตรวจแล้วในรอบนี้:

- Backend: 26 tests ผ่าน รวมเสียงเงียบ เสียงโทนและเสียงรบกวนที่ต้องไม่กลายเป็นคำถาม

- เพิ่ม `scripts/prepare_thai_stt.py` สำหรับเตรียมโมเดลและ tokenizer แบบตรึงเวอร์ชัน

## งานที่ยังต้องทดสอบ

1. ไมค์จริงใน Chrome: การอนุญาตไมค์, การตัดช่วงเงียบ และการเล่นเสียงตอบ
   อัตโนมัติ. รอบนี้ตรวจผ่าน HTTP/API; computer-use หยุดเพราะยืนยัน URL
   ของ Chrome ไม่ได้ จึงยังไม่ได้ตรวจพฤติกรรมบนหน้าจอจริง
2. คุณภาพถอดเสียงจากสำเนียงและเสียงรบกวนจริง. โมเดลใหม่ยังอาจแบ่งคำต่างกัน
   หรือถอด “ก่อตั้ง” เป็น “ก่อนตั้ง” ในบางคลิป จึงยังต้องตรวจคำเฉพาะกับไมค์จริง
   รอบนี้เน้นภาษาไทย; ยังไม่ได้ทดสอบภาษาอังกฤษกับโมเดลที่เลือกใหม่
3. มือถือผ่าน HTTPS ที่เชื่อถือและการทดสอบใน Wi-Fi จริง
4. เครือข่ายและการส่งเสียงผ่าน SDK2 ไปยังลำโพง G1 จริง

## วิธีทำต่อ

เปิด Ubuntu 22.04 โดยตรง แล้วทำจาก root ของโปรเจกต์:

```bash
source .venv/bin/activate
# ทำครั้งแรกหากยังไม่มีโมเดลภาษาไทยใน .runtime/models
python scripts/prepare_thai_stt.py
bash scripts/run_backend.sh
```

เปิดอีก terminal ใน Ubuntu 22.04:

```bash
# ถ้า terminal ยังไม่เห็น Node ที่ติดตั้งผ่าน nvm
source "$HOME/.nvm/nvm.sh"
cd frontend
npm run dev -- --hostname 0.0.0.0 --port 3000
```

เข้า `http://localhost:3000` บนคอมเพื่อทดลองไมค์. ทดสอบบริการซ้ำได้ด้วย
`python scripts/check_web_stack.py --report .runtime/smoke-latest.json`
และเพิ่ม `--audio /path/to/question.wav` หากมีเสียงคำถามตัวอย่าง.
ดูขั้นตอนเครือข่าย/HTTPS/SDK2 ใน `README.th.md` ก่อนทดสอบส่วนหุ่นจริง.
หากคำถอดยังผิด ให้ใช้หน้า `http://localhost:3000/microphone` เพื่อเทียบ
เสียงต้นฉบับกับข้อความก่อนปรับโมเดลหรือคำใบ้เพิ่มเติม.
